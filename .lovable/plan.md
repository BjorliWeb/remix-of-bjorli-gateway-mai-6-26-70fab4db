# Fix: 13 non-canonical sitemap URLs + homepage schema validation

## A. Sitemap diagnosis

### Root cause
`public/sitemap.xml` is generated by `scripts/build-sitemap.ts`, which enumerates **every** key in the `ROUTE_SLUGS` registry across **all six locales**, plus two hardcoded "extras" blocks. It has no knowledge of which routes are actually published or prerendered. `scripts/prerender.ts` keeps a **separate, shorter** list (`ROUTES`) of routes that get real static HTML. Anything in the sitemap but not in the prerender list is served by the Cloudflare SPA fallback (`/index.html`), which is the prerendered **homepage** — so the crawler sees the homepage title, homepage description and `<link rel="canonical" href="https://bjorli.no/">`.

Verified live (all HTTP 200, no redirect, all returning the homepage document):

```text
/sommer/tafjordfjella/   -> title "Bjorli | Sommer, fjell, ..."  canonical https://bjorli.no/
/praktisk-info/          -> same
/en/ski-holiday-norway/  -> same
/ski-holiday-norway/     -> same
```

### The three invalid groups (13 URLs)
1. **praktisk-info x6** — `praktisk-info` is in `ROUTE_SLUGS` but the page is **deliberately unpublished**: `src/App.tsx` does not import `PracticalInfo` and the route falls through to NotFound; `scripts/prerender.ts` lists it under both the "do not prerender" note and `EXCLUDED_FROM_COVERAGE`. Only the sitemap still emits it.
2. **sommer/tafjordfjella x6** — these **are real routes** (`src/App.tsx` renders `<Tafjordfjella />` at `/sommer/tafjordfjella` and at the localized `sommer` slugs) and `src/lib/seo/routeSeo.ts` already has a per-locale `'sommer/tafjordfjella'` SEO entry. They are broken only because they were never added to the prerender list, so crawlers get homepage HTML.
3. **/en/ski-holiday-norway x1** — invented path. The router has exactly one route: `/ski-holiday-norway` (no locale prefix), `src/App.tsx` line 195. The `EN_ONLY_EXTRAS` block in `scripts/build-sitemap.ts` prefixes it with `/en`. It is also not prerendered, so even the correct `/ski-holiday-norway/` currently serves homepage HTML.

### Correct route for Ski Holiday Norway
`https://bjorli.no/ski-holiday-norway/` — EN-only, no `/en` prefix, self-canonical once prerendered.

### Ski Holiday Norway metadata: one source of truth (required)
The title and description already exist in the CMS fixture `SEO_LANDING_FIXTURES['en/ski-holiday-norway']` (`src/lib/cms/mockAdapter.ts`, `seoTitle` / `seoDescription`). They will be **moved, not copied**, into a new dependency-free module `src/lib/seo/skiHolidayNorwaySeo.ts` exporting `SKI_HOLIDAY_NORWAY_PATH` and `SKI_HOLIDAY_NORWAY_SEO { title, description }`. Wording unchanged.

Consumers all read that module:
- `src/lib/cms/mockAdapter.ts` — fixture references the constants.
- `src/lib/seo/routeSeo.ts` — EN-only entry `['ski-holiday-norway'].en` built from the constants, so `SEOHead` / `seoForCanonicalPath` resolve them.
- `src/pages/SkiHolidayNorway.tsx` — `PAGE_URL` becomes `/ski-holiday-norway` (was `/en/ski-holiday-norway`) and the CMS-missing fallback `PageMeta` uses the constants.
- `scripts/prerender.ts` — imports the same module (build-time safe: no React, no image imports).

### Files that should change
- `scripts/prerender.ts` — add the two real pages so they emit self-canonical HTML.
- `scripts/build-sitemap.ts` — remove `praktisk-info`, fix the ski-holiday path.
- `public/sitemap.xml` — regenerated output only (never hand-edited).

### Exact entries to remove or correct
| Where | Change |
|---|---|
| `build-sitemap.ts` `EXCLUDE_CANONICAL` | add `'praktisk-info'` (removes 6 URLs) |
| `build-sitemap.ts` `EN_ONLY_EXTRAS` | `/en/ski-holiday-norway` -> `/ski-holiday-norway`; hreflang `en` and `x-default` both point at the corrected path |
| `prerender.ts` | add a `/sommer/tafjordfjella` special case (6 locales, using the existing `ROUTE_SEO['sommer/tafjordfjella']` entries) — same pattern as the existing `/handel` special case |
| `prerender.ts` | add a `/ski-holiday-norway` special case (EN only). Requires one SEO entry sourced from the title/description already present in `src/pages/SkiHolidayNorway.tsx` — no new copy invented |

If prerendering `/ski-holiday-norway` is judged out of scope, the fallback is to drop it from the sitemap entirely rather than keep a URL that serves homepage HTML. Recommendation: prerender it — it is a real page.

## B. Structured-data diagnosis

### Exact validator error
> The property `inLanguage` is not recognised by the schema (e.g. schema.org) for an object of type `TouristDestination`.

`inLanguage` is defined on `CreativeWork` / `Action`, not on `Place` or its subtype `TouristDestination`.

### Live homepage JSON-LD (two blocks)
```json
{"@type":"WebPage","name":"…","description":"…","url":"https://bjorli.no/","inLanguage":"nb-NO",
 "isPartOf":{"@type":"WebSite","name":"bjorli.no","url":"https://bjorli.no"}}
```
```json
{"@type":"TouristDestination","name":"Bjorli","description":"…","url":"https://bjorli.no/",
 "inLanguage":"nb-NO","address":{"…"},"telephone":"+4748152200","geo":{"…"}}
```
The `WebPage` block is valid — `inLanguage`, `isPartOf`, `url`, `description` are all correct there. Ahrefs lists `WebPage` alongside `TouristDestination` because it reports every type present on a failing page, not because `WebPage` itself is invalid.

### Schema type / invalid property
`TouristDestination` -> `inLanguage`. Every other property in that block (`name`, `description`, `url`, `address`, `telephone`, `geo`) is valid.

### Source files
- `src/components/SEOHead.tsx` line ~292 — runtime block, `id="jsonld-org"`.
- `scripts/prerender.ts` lines ~296-305 (`touristDestinationLd`) — prerendered block, same `id`.

Both must change together, otherwise hydration reintroduces the bad property.

### Whether all locales share it
Yes — the same builder runs for `no/en/de/nl/da/sv`, which is exactly the 6 homepage URLs Ahrefs flags. `https://www.bjorli.no/` serves the identical prerendered homepage on the duplicate host, so it is one issue, not two.

### Proposed minimal correction
Delete the `inLanguage` line from the `TouristDestination` object in both files. Nothing else changes: the language signal is already carried by `<html lang>`, `og:locale`, hreflang, and the `WebPage` block's own valid `inLanguage`. No new properties added, neither type removed.
